# 异步模式手册

## 一、先看模式

工具列表里有没有 `job_status`，就是答案

| 看得到 `job_status` | 说明                                              |
| ------------------- | ------------------------------------------------- |
| 是                  | 异步模式开启，按本文走                            |
| 否                  | 异步模式关闭，`bash` 就是普通同步工具，本文不适用 |

## 二、`bash` 的行为

```
bash("git status")   →  20 秒内跑完  →  直接给结果        ← 大多数命令
bash("npm test")     →  20 秒没完    →  返回作业号         ← 慢命令
                         命令继续在后台跑，结果稍后送来
```

**看拿到的是结果还是作业号，就知道该干什么**

| 拿到什么            | 该做什么               |
| ------------------- | ---------------------- |
| 结果（命令输出）    | 正常继续               |
| 作业号（如 `P3AD-1`） | 这一步已结束，**别等** |

多个作业同时完成会合并成一条消息，前面加 `[N background jobs finished]`

## 三、拿到作业号之后

**拿到作业号就是这一轮的终点** 记下编号，转身做别的

**手上一件可做的事都没有时，直接结束这一轮** 不必为了填满这一回合而写点什么，也不需要找理由继续——结果到达时会作为新消息把你叫醒

**三条禁令**（每条都是踩过的坑）：

1. **不要轮询**、不要重跑同一个命令、不要指望同一回合拿到结果
2. **不要写长文**——结果没到，写的"总结"没有信息增益，还会把结果往后推
3. **不要汇报"我提交了后台任务"**——用户屏幕上直接看得到。只在**结果回来**时说话

判据：你正要写的这句话，**用到了那个还没到的结果吗** 没用到 → 不必写

## 四、`expectSeconds` 与 `mode`

两个参数只干一件事：**决定 `bash` 在返回作业号之前等多久**

| 给什么                | 行为                         |
| --------------------- | ---------------------------- |
| 什么都不给            | 等 20 秒，没完转后台         |
| `expectSeconds` < 120 | 等满你估的秒数，没完再转后台 |
| `expectSeconds` ≥ 120 | 一秒都不等                   |
| `mode: "background"`  | 一秒都不等                   |

**`expectSeconds` 问的是「任务要多久」，不是「我愿意等多久」**

估低了不要紧——命令照跑，结果会送来，代价只一轮往返。估高了更差——**超过 120 秒就拿不到内联结果**

```
bash(command: "./audit.ps1", expectSeconds: 45)   ← 估 45 秒，会等满
bash(command: "npm install", mode: "background")  ← 明知慢，一秒不等
```

**别把 `expectSeconds` 当 `timeout`**——后者管「多久杀掉」

**两个参数大多数时候都不用写**：默认 20 秒够用

特殊情况是，当你认为这个任务只需要略微超过 20 秒钟一点，比如这个任务需要跑 25 秒或者 30 秒钟—这个时候转后台没过几秒钟再转回来，明显没有性价比。这时你便可以加入等待，多等几秒钟来换取结果

## 五、适合什么

| 适合                   | 为什么                 |
| ---------------------- | ---------------------- |
| 跑测试套件、构建、编译 | 等待期间可以改别的文件 |
| 装依赖                 | 同上                   |
| 跑端到端验证、长脚本   | 几十秒到几分钟起步     |

**一次可以丢多个**，同时跑 7 个，超出的自动排队。并行 `bash` 调用即可

**不要用异步的场景**：两个任务要改同一个文件（会冲突）；任务之间有依赖（异步传不了结果）

## 六、硬性约束

1. **后台作业没有 stdin**。`vim`、`ssh`、`psql` 会一直挂着直到超时。写命令时确保输出完就退出
2. **扩展重载会终止所有运行中的作业**。重载后旧作业在下次启动时标为 `failed`（`interrupted`）——那意味着被中断，不是正常结束。**不要因此重试同样的命令**，先搞清楚它跑到哪了
3. **并发上限 7**。超出的排队，槽位释放后自动启动
4. **`kill` 会杀整棵进程树**，等进程真没了才返回。Windows 上可能残留孤儿进程，此时结果里标 `leaked`

## 七、查作业

| 工具          | 作用                             |
| ------------- | -------------------------------- |
| `job_status`  | 当前会话所有后台作业的状态和结果 |
| `job_logs`    | 某个作业的实时输出               |
| `job_kill`    | 停掉一个作业                     |
| `job_history` | 历史日志，跨会话可查             |

**`job_status` 只列真正的后台作业** 宽限期内跑完、结果内联返回的命令不进表——没看到它们是对的，不是丢了

**`job_status` 与 `job_history` 的区别：**

|              | `job_status`   | `job_history`    |
| ------------ | -------------- | ---------------- |
| 数据来源     | 内存里的作业表 | 磁盘上的日志文件 |
| 新会话能看到 | **看不到**     | **看得到**       |
| 重载扩展后   | 清空           | **保留**         |

**要查上个会话的作业编号，只有 `job_history` 查得到**

**不要轮询** 启动后干自己的事，结果会自己找来。只有需要**中途**查看进度时才用 `job_status` / `job_logs`

## 八、一句话判据

> **"除了等它，我还能不能干别的？"**
> 能 → 让它后台跑，自己去做别的
> 不能 → 结束这一轮，结果会送来

**没有"把 `expectSeconds` 写很大来强行等"这条路**——超过 120 秒它只会直接转后台
