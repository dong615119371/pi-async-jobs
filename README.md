# async-jobs

我们为 Pi 的 agent loop 加入了「后台作业」能力！慢命令不再占住整个回合！

> ⚠️ 这个插件目前还处于实验性质的架构探索插件 如需使用在生产场景上 请谨慎使用！
>
> **本项目的绝大部分代码由 vibe coding 生成**，请带着这个前提使用和审阅。

## 怎么工作的

实现原理简单到让人不可思议 简单来说，这个插件就是让长命令不再跑满它应该有的时间。

当运行一个长任务命令时，只等待一个默认数值的时间，（当然用户可自行修改）随后当默认时间跑满并且命令仍未返回结果，将强制使其后台运行，并返还给 Agent 一个任务编号，以此唤醒 Agent 继续完成目前工作中不依赖命令结果的任务。

到了后台命令完成时，将会把运行结果返还给 Agent，再次唤醒了 Agent，使其可以针对结果做工作。

```
bash(command)
   │
   ├─ 异步模式关闭 ──→ Pi 自带 bash（同步，行为不变）
   │
   └─ 异步模式开启
        │
        ├─ 宽限期内结束 ──→ 结果内联返回，本回合结束
        │
        └─ 超过宽限期 ──→ 落盘 + 返回作业号，本回合结束
                            │
                    进程继续在后台跑
                            │
                ┌─────────┴─────────┐
            正常结束 / 失败        job_kill
                │                      │
           3 秒合并窗口          杀整棵进程树
                │                 + 确认退出
                ↓                      ↓
        唤醒 Agent（新回合）        标记 killed
                                    不通知
```

宽限期默认 20 秒。`mode: "background"` 或 `expectSeconds ≥ 120` 时跳过等待，直接走右下那条。

## 核心特性

| 特性                 | 说明                                                                      |
| -------------------- | ------------------------------------------------------------------------- |
| bash 自动后台化      | 异步模式开启后，命令超过宽限期仍未结束就转后台，返回作业号                |
| `expectSeconds`      | 给出**任务耗时**估计来决定等多久。不杀命令、不限运行时长                  |
| `mode: "background"` | 完全不等待，立即返回作业号                                                |
| 作业持久化           | 记录原子落盘（先写 `.tmp` 再改名）；重启后遗留的 `running` 标为 `failed`  |
| 结果主动送达         | 完成或失败的作业自动唤醒 Agent；多个作业按 3 秒窗口合并；被 kill 的不再通知 |
| 四个工具             | `job_status` / `job_logs` / `job_kill` / `job_history`                    |
| 渠道注册表           | 渲染器可插拔。框架只内置 `generic`，其他渠道由对应扩展自行注册            |
| 进程树终止           | `kill` 终止整棵进程树，等进程真正退出才返回                               |

> 这些工具默认**未激活**。`bash` 覆盖始终注册，但异步模式关闭时转发给 Pi 自带的 bash，行为不变。

## 安装

**推荐从 git 安装**，可以锁定版本：

```bash
pi install git:github.com/dong615119371/pi-async-jobs@v0.1.2
```

不带 `@v0.1.2` 会装最新的 `main`，适合想跟开发进度的情况。

也可以直接用目录：把 `async-jobs/` 整个拷进 Pi 的 extensions 目录（位置随安装方式不同，见 Pi 官方文档）。

运行时数据落在 `<Pi agent dir>/async-jobs/`：

| 文件                           | 内容                       |
| ------------------------------ | -------------------------- |
| `<id>.json`                    | 作业记录（原子写）         |
| `<id>.output`                  | 作业输出                   |
| `job-history-YYYY-MM-DD.jsonl` | 持久历史（保留今天与昨天） |
| `mode.json`                    | 异步模式开关               |
| `config.json`                  | 宽限期配置                 |

## 快速开始

异步模式默认关闭，先打开：

```bash
/async on     # 开启，Agent 才能看到后台工具
/async        # 查看当前状态
/async off    # 关闭（已跑的作业不受影响）
```

先说一个实际用例。用户让 Agent 跑一遍测试：

```text
用户：跑一下测试
Agent：bash(command: "pytest -q")
       ↓ 等待时长到达阈值，命令仍未返回
         强制转后台，不再继续等待它的结果
       "作业 aj-3f9c1d2e 已在后台运行，结果会自己送回来。"

用户：那先把 README 里的安装章节改成 npm
Agent：（接着改 README，无需等测试）

       ⋮ 一分钟后

Agent：（收到作业结果）测试跑完了：3 failed, 47 passed。
```

关键点：命令超过设定的等待阈值后，强制转后台并且不再继续等待它的结果；Agent 可以接着做那些不需要（或不必等）这个结果的其它任务。那个回合到这里就结束了，作业结果会在新的一回合里回来。

参数怎么给：

```text
bash(command: "git status")
  → 不传 expectSeconds：按默认宽限期（20 秒）等，秒回就正常返回结果

bash(command: "npm run build", mode: "background")
  → 完全不等待，立即转后台

bash(command: "pytest -q", expectSeconds: 45)
  → Agent 估它要跑 45 秒：就等 45 秒，到了还没完就转后台
```

结果会自己送回来，无需轮询。需要主动查看时用工具：

```text
job_status                   # 列出后台作业（可 cleanup / verbose）
job_logs aj-1a2b3c4d         # 看某作业的最新输出
job_kill aj-1a2b3c4d         # 停止某作业
job_history                  # 翻历史作业（跨会话）
```

用户也可直接用斜杠命令：`/jobs`、`/job-logs <id>`、`/job-kill <id>`、`/job-history [count]`。

## 工具参考

| 工具          | 用途                         | 关键参数                                                               |
| ------------- | ---------------------------- | ---------------------------------------------------------------------- |
| `job_status`  | 列出本会话的后台作业并读结果 | `jobs`（省略=全部）、`cleanup`（删已完成记录）、`verbose`（完整结果）  |
| `job_logs`    | 读某作业的最新输出           | `id`（接受唯一前缀）、`maxBytes`（默认 4000）。从输出文件尾部读        |
| `job_kill`    | 停止运行中的作业             | `id`、`reason`。整棵进程树终止，等进程真没了才回                       |
| `job_history` | 持久历史，旧的在前           | `count`（默认 **20**，范围 1–200）、`id`、`full`。跨重启、跨 `/reload` |

`job_status` 只列真正的后台作业——宽限期内跑完、结果内联返回的命令不算。

`/job-history [count]` 斜杠命令默认取 **15** 条，与工具的 20 不同。

## expectSeconds 决策表

它估的是**任务耗时**，不是「Agent 愿意等多久」。

| 取值            | 行为                                      |
| --------------- | ----------------------------------------- |
| 省略 / 非有限数 | 用默认宽限期（20 秒），到时仍运行就转后台 |
| `x < 120`       | 按 x 秒等待，到时仍运行就转后台           |
| `x ≥ 120`       | 完全不等待，立刻返回作业号                |

写大数字不会更快拿到结果——它只会立刻转后台。低估是安全的：命令照跑，结果作为消息回来，只多一个来回。所以已知很长的任务（安装、克隆、构建、整套测试）不要估，直接 `mode: "background"`。

## 默认值一览

| 项         | 值                                                                                  |
| ---------- | ----------------------------------------------------------------------------------- |
| 默认宽限期 | 20 秒（`config.json` 里 `graceSeconds` 可改，每次调用读取）                         |
| 并发上限   | 7（超出排队，槽位释放后自动启动）                                                   |
| kill 上限  | 普通 15 分钟 / 长任务 45 分钟 / **已自行后台化的命令 30 分钟**；显式 `timeout` 优先 |

第三档指命令命中 `nohup`、`setsid`、`Start-Process`、`Start-Job` 或结尾单个 `&`——这些不加自动上限，回退 30 分钟。

## 已知限制

- **只在 Windows 上开发与验证。** 进程树终止用 `taskkill /T`（再 `/F`），shell 解析查找 Git Bash。代码里有 POSIX 分支（进程组信号、`/bin/sh`），但**未经测试**。
- **进程树终止可能残留孤儿进程。** 是否终止依赖存活探测；探测不可靠时无法保证整棵子树都已结束，此时仅在结果里标记 `leaked`。

## 设计说明

**没有动任何底层架构。** 整个插件的原理实现非常简单 整个是以轻量级应用层的方式实现。也正因为如此，它才停留在实验性质的架构探索阶段。

**为什么改工具侧而不改 loop。** loop 同步是刻意的：工具必须先返回，Agent 才能接着生成。让慢命令不阻塞只有两条路——改 loop，或在工具层把「等待」抽走。这里选后者：进程照常启动，只把「报告」改成「先给作业号、结果后到」。改动面小，不碰 Pi 的核心。

**渠道注册表做什么。** 框架会跑进程、跟踪、杀掉、落盘、送达，但它不知道某个渠道的输出流长什么样——那份知识属于贡献该渠道的扩展。`channels.ts` 让扩展注册 `render` / `digest`，框架按 `record.channel` 查表。于是加渠道不用改本包，卸掉某个渠道扩展也不影响其他渠道；没注册渲染器的作业走内建回退，照样送达。

**为什么 kill 要等进程真死。** `child.kill()` 只信号直接子进程，它派生的孙子进程会活着。所以先杀整棵树（Windows 上 `taskkill /T`，再 `/F` 兜底），再用存活探测确认进程真没了才返回——「发了信号」和「已经没了」是两回事。

## 输出编码

子进程吐的是裸字节，没有标签说它是什么编码。解码错了就是乱码，而乱码容易被当成别的问题去查。

实际案例：

```
wsl.exe 真实输出：未安装适用于 Linux 的 Windows 子系统…
一律按 UTF-8 解： *g?[??(u?N  L i n u x  ...
按 UTF-16LE 解：  未安装适用于 Linux 的 Windows 子系统…
```

`wsl.exe` 输出 UTF-16LE。这个现象当时被误判成 shell 出错。所以不能假定 UTF-8。

### 判定方式

不猜编码。把同一批字节按四种候选各解一遍，数谁解出来的坏东西最少。

| 候选                | 缺陷计数                                      |
| ------------------- | --------------------------------------------- |
| UTF-8               | `U+FFFD` 替换字符个数                         |
| UTF-16LE / UTF-16BE | 孤立代理对、`U+FFFE`/`U+FFFF`、可打印字符过少 |
| GBK                 | `U+FFFD` 个数                                 |

不需要预设表，也不需要知道内容是什么语言。

### 四条细节

**一、末尾半截字符不计缺陷。** 数据切在多字节字符中间时，最后那个字符只是还没到齐。算成缺陷会让正确编码显得更差——64 字节 UTF-8 切片（切口落在汉字中间）得 1 个缺陷，GBK 得 0，正确的反而输。

**二、UTF-8 零缺陷直接定案。** GBK 编码空间很宽，几乎任意字节对都「合法」，干净的 UTF-8 在它眼里也是零缺陷。只按最小缺陷比会平局，让 GBK 靠并列篡位。规则是干净的 UTF-8 不被并列者取代。

**三、检测和解码用同一个对齐偏移。** UTF-16 可能错位一字节。`scoreUtf16` 返回分数也返回偏移量：检测按偏移 1 算分、解码从偏移 0 开始，输出会前几个字对、后面全是噪音。

**四、缺陷数要和可打印字符数一起看。** 错误解读往往缺陷不多，但可打印字符几乎为零。只看缺陷数会把 `wsl.exe` 判给 GBK。分数是 `缺陷 + max(0, 4 - 可打印字符数)`；另外「没有零字节且能按 UTF-8 干净解出」时判 UTF-16 不可能。

### 中文不能用零字节判断

教科书办法是「UTF-16 的奇数位有零字节」：

```
"ABC" UTF-16LE = 41 00 42 00 43 00   ← 有零，能认出来
"中文" UTF-16LE = 2d 4e 87 65         ← 一个零都没有
```

中文在 UTF-16LE 里全非零，零字节法直接失效。所以零字节检查只是**加分项**，不是必需条件。

### 流式输出

管道按块读，一个汉字在 UTF-8 里占 3 字节，可能被切开：

```
chunk1 = E4 B8        ← 「中」的前两字节
chunk2 = AD 41 42     ← 「中」的第三字节 + 「AB」
```

单独解 chunk1 会得到 `U+FFFD`，而且**无法修复**——字节已经解错。`StreamDecoder` 把尾巴留着，等下一块拼上再解。

UTF-8 的半截长度能精确算：首字节自己声明序列长度（`110xxxxx` 2 字节、`1110xxxx` 3 字节、`11110xxx` 4 字节），不够就是半截。UTF-16 更简单：奇数字节就是半截。

头 32 字节不下结论（`DECIDE_AFTER_BYTES`），样本太小时什么解读都可能看着干净。代价是最前面几十字节输出会延迟，日志里看不出来。

### 局限

- **GBK 半截字符不检测。** UTF-8 能精确算出缺几个字节，GBK 双字节没这个信息，切在半路时无法判断是半截还是完整。GBK 流被切断时会出现替换字符。
- **不足 32 字节的短输出是赌。** 样本不够时几种解读都零缺陷，只能靠「平局给 UTF-8」兜底。
- **合法的 GBK 字节序列恰好构成合法 UTF-8 时，会被当成 UTF-8。** 概率低但不是零，这是用「UTF-8 最常见」换掉一次比较。

覆盖 Windows 上实际会遇到的四种编码，对中文有效，对切块鲁棒。比「一律 UTF-8」强一个数量级，比引入完整编码检测库轻两个数量级。

## 跑测试

共 10 个测试文件（`async-jobs/_*.mts`），逐个用 `node` 跑：

```bash
node async-jobs/_smoke.mts
node async-jobs/_grace.mts
node async-jobs/_gracepolicy.mts
node async-jobs/_batch.mts
node async-jobs/_channels.mts
node async-jobs/_encoding.mts
node async-jobs/_journal.mts
node async-jobs/_status.mts
node async-jobs/_timeout.mts
node async-jobs/_stress.mts
```

需要 Node 能直接运行 TypeScript（类型剥离）。

每个文件逐条打印 `PASS`，结尾一行汇总：

```text
====================================================
PASS 34   FAIL 0
```

全部通过时进程退出码为 0，任意一条失败则为 1。总共 **401 条断言**，分在 10 个文件里；跑完 _smoke 和 _stress 需要几分钟（它们在真实地 spawn 进程）。
